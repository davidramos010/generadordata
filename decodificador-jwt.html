      Guía de JWT
      
                
      
                    
      
                        
      ¿Qué es un JWT?
      
                        
      Un JSON Web Token (RFC 7519) es un texto compacto que transporta datos —quién es el usuario, qué puede hacer, hasta cuándo— firmados por quien los emite. Es autocontenido: la API que lo recibe no necesita consultar una base de datos de sesiones, le basta con comprobar la firma. Por eso se usa tanto en APIs, microservicios e inicio de sesión único.
      
                        
      
                        
      Estructura
      
                        
      Tiene tres partes en Base64URL separadas por puntos:
      
                        
      encabezado.carga útil.firma
      
                        
        
                            
      • Encabezado: el algoritmo de firma (alg), el tipo (typ) y a veces el identificador de la clave (kid).
        • 
                            
      • Carga útil: los claims, es decir, los datos del token.
        • 
                            
      • Firma: se calcula sobre encabezado.carga con un secreto o una clave privada. Si alguien cambia una sola letra, deja de coincidir.
        • 
                        
      
                    
      
                    
      
                        
      ⚠️ Codificado no es cifrado
      
                        
      Cualquiera que tenga el token puede leer su carga útil: Base64URL no oculta nada. La firma garantiza que nadie lo ha modificado, no que nadie lo haya leído. No metas contraseñas, datos bancarios ni información personal sensible en un JWT. Si necesitas confidencialidad, usa JWE (tokens cifrados, de 5 partes).
      
                        
      
                        
      ¿Cuándo usar JWT?
      
                        
        
                            
      • APIs y microservicios: cada servicio valida el token por su cuenta, sin estado compartido.
        • 
                            
      • Inicio de sesión único (SSO) y OpenID Connect: el ID token es un JWT.
        • 
                            
      • Apps móviles y SPA que llaman a APIs con un token de acceso.
        • 
                            
      • Funciones serverless, donde no hay sesión en memoria.
        • 
                        
      
                        
      No es la mejor opción cuando necesitas revocar sesiones al instante (cerrar la sesión de un usuario ya): un JWT sigue siendo válido hasta que caduca. Ahí encajan mejor las sesiones en servidor o los tokens opacos.
      
                    
      
                
      
            
      
        
      

        
      
            
      
                
      Claims registrados
      
                
      
                    
      
                        
      
                            
      
                                
      ClaimNombrePara qué sirve
      
                                
                                
      issEmisor (issuer)Quién creó y firmó el token, por ejemplo https://auth.ejemplo.com. Compruébalo siempre al verificar.
      
                                
      subSujeto (subject)A quién se refiere el token: normalmente el identificador único del usuario.
      
                                
      audAudiencia (audience)Para qué API o aplicación es el token. Puede ser un texto o una lista; tu API debe rechazar tokens que no la incluyan.
      
                                
      expCaducidad (expiration)Fecha en segundos desde 1970 a partir de la cual el token ya no vale. Limita el daño si el token se filtra.
      
                                
      nbfNo antes de (not before)Fecha antes de la cual el token todavía no es válido.
      
                                
      iatEmitido en (issued at)Cuándo se creó el token; sirve para saber su antigüedad.
      
                                
      jtiID del token (JWT ID)Identificador único del token; permite detectar si se reutiliza o revocarlo en una lista negra.
      
                                      
                            
      
                        
      
                        
      Además de estos, los proveedores añaden claims propios: scope (permisos), azp (cliente autorizado), nonce (protección del inicio de sesión en OpenID Connect) o cualquier dato de tu aplicación, como role. Los ID tokens de OpenID Connect describen al usuario para la aplicación que inicia sesión; los access tokens autorizan llamadas a una API y su audiencia es esa API.
      
                    
      
                
      
            
      
        
      

        
      
            
      
                
      Algoritmos de firma
      
                
      
                    
      
                        
      HS256 / HS384 / HS512 · secreto compartido
      
                        
      HMAC con SHA-2. El mismo secreto firma y verifica, así que todos los que verifican también pueden emitir tokens. Úsalo solo cuando el emisor y el receptor son el mismo sistema. El secreto debe ser aleatorio y de al menos 32 bytes para HS256 (48 y 64 para HS384 y HS512); uno corto se adivina por fuerza bruta en minutos.
      
                        
      
                        
      RS256 / RS384 / RS512 · RSA
      
                        
      Se firma con una clave privada y se verifica con la pública, que se puede publicar en un JWKS. Es el más compatible. Usa claves de al menos 2048 bits. Los tokens PS256/384/512 (RSA-PSS) se pueden decodificar aquí, pero no verificar ni firmar.
      
                    
      
                    
      
                        
      ES256 / ES384 / ES512 · curvas elípticas
      
                        
      ECDSA sobre las curvas P-256, P-384 y P-521. Ofrece la misma seguridad que RSA con claves y firmas mucho más pequeñas, por lo que los tokens son más cortos. Cada algoritmo exige su curva: ES256 solo funciona con P-256.
      
                        
      
                        
      EdDSA · Ed25519
      
                        
      La opción más moderna: firmas rápidas, deterministas y difíciles de implementar mal. Comprueba que todas tus librerías y proveedores lo admiten antes de adoptarlo.
      
                        
      
                        
      ¿Cuál elegir?
      
                        
      Si varias aplicaciones verifican tokens que emite un único servidor, usa uno asimétrico (RS256 por compatibilidad o ES256/EdDSA por tamaño y rendimiento). Reserva HS256 para un único servicio que firma y verifica.
      
                    
      
                
      
            
      
        
      

        
      
            
      
                
      Cómo verificar un JWT correctamente
      
                
      
                    
      
                        
      Los pasos, en este orden
      
                        
        
                            
      1. Fija la lista de algoritmos aceptados en tu código (por ejemplo, solo RS256). Nunca uses el alg que llega en el token para decidir cómo verificarlo.
        2. 
                            
      2. Comprueba la firma con la clave correspondiente: el secreto para HS*, la clave pública o el JWKS del emisor para el resto. Si hay kid, úsalo para elegir la clave del JWKS.
        3. 
                            
      3. Comprueba las fechas: exp en el futuro y nbf en el pasado, con un margen de unos 60 segundos por diferencias de reloj.
        4. 
                            
      4. Comprueba iss y aud: que el emisor es el esperado y que el token es para tu API.
        5. 
                            
      5. Solo entonces, usa los claims (permisos, usuario…).
        6. 
                        
      
                    
      
                    
      
                        
      PHP (firebase/php-jwt)
      
                        
      use Firebase\JWT\JWT;
use Firebase\JWT\Key;

JWT::$leeway = 60; // margen de reloj en segundos
$claims = JWT::decode($token, new Key($clavePublica, 'RS256'));
if ($claims->iss !== 'https://auth.ejemplo.com') {
    throw new Exception('Emisor no válido');
}
      
                        
      
                        
      Node.js (jose)
      
                        
      import { jwtVerify, createRemoteJWKSet } from 'jose';

const JWKS = createRemoteJWKSet(
  new URL('https://auth.ejemplo.com/.well-known/jwks.json'));
const { payload } = await jwtVerify(token, JWKS, {
  issuer: 'https://auth.ejemplo.com',
  audience: 'api.ejemplo.com',
  algorithms: ['RS256'],
});
      
                        
      
                        
      Generar claves de prueba
      
                        
      openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out rsa.pem
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out ec.pem
openssl genpkey -algorithm ED25519 -out ed.pem
openssl pkey -in rsa.pem -pubout -out rsa.pub   # clave pública
      
                    
      
                
      
            
      
        
      

        
      
            
      
                
      Seguridad: errores habituales
      
                
      
                    
      
                        
      🚫 alg «none»
      
                        
      Un token con "alg": "none" no tiene firma: cualquiera puede escribir lo que quiera en él. Las librerías antiguas lo aceptaban si no se fijaba el algoritmo. Esta herramienta lo decodifica con un aviso y nunca lo da por verificado.
      
                        
      
                        
      🔀 Confusión de algoritmos
      
                        
      Si un servidor verifica con «la clave que tenga» y usa el alg del token, un atacante puede firmar un token HS256 usando como secreto la clave pública RSA, que es pública, y el servidor lo aceptará. La defensa es fijar los algoritmos permitidos y no mezclar secretos con claves públicas. Aquí un token HS* solo se verifica con un secreto y uno RS/ES/EdDSA solo con una clave pública.
      
                        
      
                        
      ⏱️ Caducidad corta
      
                        
      Un JWT no se puede revocar fácilmente: si se filtra, vale hasta exp. Usa caducidades cortas (de 5 a 60 minutos para access tokens) y tokens de actualización para renovarlos.
      
                    
      
                    
      
                        
      🔑 Secretos y claves
      
                        
      Genera los secretos HMAC con un generador aleatorio (por ejemplo, openssl rand -base64 32), nunca a mano. Guárdalos en variables de entorno o en un gestor de secretos, no en el código. Rota las claves y publica las nuevas en el JWKS antes de retirar las antiguas.
      
                        
      
                        
      🔒 Privacidad de esta herramienta
      
                        
      El token se decodifica en tu navegador. Solo viaja al servidor —por HTTPS— cuando pulsas Verificar firma o Generar JWT; se procesa en memoria y no se guarda ni se registra. Los campos de claves se vacían al salir de la página. Las direcciones JWKS se descargan con protecciones: solo https, nunca redes privadas, sin redirecciones y con límite de tiempo y tamaño.
      
                        
      
                        
      ¿Por qué no hay botón «Compartir»?
      
                        
      Otras herramientas meten el token en la URL para compartirlo. Una URL queda en el historial del navegador, en los registros de los servidores y en las herramientas de analítica: un token válido compartido así es una credencial filtrada. Si necesitas enseñar un token, comparte uno caducado o de pruebas.
      
                    
      
                
      
            
      
        
      

        
      
            
      
                
      Preguntas frecuentes sobre JWT
      
                
      
                    
      
                        
      ¿Es seguro pegar un JWT en esta herramienta?
      
                        
      El token se decodifica en tu navegador y solo se envía al servidor cuando pulsas Verificar firma o Generar JWT. Se procesa en memoria y no se guarda ni se registra. Aun así, un JWT válido es una credencial: para pruebas usa tokens caducados o de entornos de desarrollo, nunca tokens de producción en vigor.
      
                        
      
                        
      ¿Qué diferencia hay entre decodificar y verificar un JWT?
      
                        
      Decodificar solo convierte el encabezado y la carga útil de Base64URL a JSON para leerlos; cualquiera puede hacerlo sin ninguna clave. Verificar comprueba con el secreto o la clave pública que la firma es correcta, es decir, que el token lo emitió quien dice y que nadie lo ha modificado.
      
                        
      
                        
      ¿Por qué la firma de mi token aparece como no válida?
      
                        
      Las causas habituales son usar un secreto o una clave pública distintos de los que firmaron el token, marcar o desmarcar por error «Codificado en Base64» en un secreto HMAC, pegar el token incompleto, o verificar con un JWKS que ya no contiene la clave indicada en el kid del encabezado.
      
                        
      
                        
      ¿Qué algoritmos admite?
      
                        
      Verifica y firma HS256, HS384, HS512, RS256, RS384, RS512, ES256, ES384, ES512 y EdDSA (Ed25519). Los tokens PS256, PS384 y PS512 se pueden decodificar, pero no verificar ni firmar. Los tokens sin firma (alg none) se decodifican con un aviso y nunca se dan por verificados.
      
                        
      
                        
      ¿Un JWT está cifrado?
      
                        
      No. Un JWT firmado solo está codificado en Base64URL: cualquiera que lo tenga puede leer su contenido. La firma impide modificarlo, no leerlo. Por eso no debes guardar contraseñas ni datos sensibles en la carga útil; si necesitas confidencialidad, usa JWE (tokens cifrados).
